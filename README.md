# post-collector 使用手册

## 这是什么

一个装在自己机器上的内容收纳工具。它从**你自己拥有或已获明确授权**的来源（自建频道、自己的账号导出、你管理的群、RSS 等）把图文内容收进来，去重、清理、打标签，然后让你按标签、关键词、来源、时间、类型把它们搜出来。

它解决的是「东西太多、散得到处都是、想找的时候找不到」。它不是公开图站，也不做内容分发：默认只监听本机或内网，默认不把任何内容发到外部服务。

安装与运行时也不需要任何常驻服务：数据库就是数据根目录下的**一个 SQLite 文件**，它同时承担事实源、任务队列与全文索引。

## 它刻意不做的事

下面这些不是「以后再说」，而是设计上明确排除，写在这里免得你反复期待：

- 不绕过登录、验证码、平台限流，不抓非公开内容；
- 不做公开分享站点，不做内容再分发；
- 不做多人 SaaS，不做实时聊天客户端；
- 不给匿名提报者任何账号、历史记录或检索能力；
- 不把内容送去第三方 AI：当前版本连外发代码路径都不存在。

## 现在能用到什么程度

这一版是**骨架**，先把地基、数据结构和接口画对。功能按 DESIGN.md 的路线图分三阶段交付，当前进度如下：

| 能力 | 当前状态 |
| --- | --- |
| 目录结构、13 个可替换的接口、设置项声明 | 已完成 |
| 环境体检命令 `pc doctor`（含只读数据库段与运行时目录段） | 已完成，现在就能用 |
| 数据库：SQLite 建库、34 张表、FTS5 双索引、迁移应用与结构校验 | **已完成**，见第 3 步与「日常操作」 |
| 设置层：生效值与来源可查、首次启动播种（命令行） | **已完成**，见「参数怎么调」；设置页界面在阶段 1 |
| **把你的本地文件放进库**（来源登记 → 导入/上传 → 处理 → 查看） | **已完成**，见「把你的文件放进去」 |
| 采集安全底线（魔数校验、类型白名单、字节上限、隔离区物理分离、SHA-256 精确去重） | **已完成**；缩略图、感知哈希与病毒引擎还没做 |
| **按关键词与过滤器检索**（`pc search`：1 字起可搜、标签/来源/时间/类型过滤、翻页、命中理由） | **已完成**，见「怎么把东西搜出来」 |

也就是说：现在可以把环境搭好、把数据库真正建起来、把**你自己的图片和文本放进库**（官方导出目录，或者你自己随手保存的文件；不需要 Docker，也不需要数据库服务），**并且用命令行把库里的东西搜出来**（中文 1 个字也能搜），把服务点着，把每个参数「现在是多少、为什么是这个值」查清楚——但还不能打标，也没有图形界面。

## 你需要准备什么

| 项目 | 要求 | 说明 |
| --- | --- | --- |
| 机器 | 4 核 CPU / 8 GB 内存起，SSD 用于数据库与近期媒体 | 有 GPU 更好，没有也能跑，只是将来本地打标慢一些 |
| 磁盘 | 一个数据目录，几百 MB 到几 GB 起；按每年约 55 GB 估（日增 100 条、平均 1.5 MB/条） | 库文件与媒体都放在这个目录下；系统内置滚动删除，可把增长压平 |
| 运行时 | Python 3.12+（自带 SQLite ≥ 3.40，启动时会校验）或 Windows 便携包 | 仓库里的开发方式用 `uv` 装依赖；不想碰命令行的人可以等阶段 1 随 Release 发布的 Windows 便携包 |
| 来源 | 至少一个你拥有或已获授权的来源 | 自己保存的文件用 `pc upload` 放进来自带的 `manual` 来源即可，**不需要任何凭证**；平台型来源才需要「凭证 + 授权范围 + 授权证明」三者齐备 |
| 网络 | 首次安装依赖需要联网；日常运行不需要 | 没有任何功能以外发为前提 |

## 五分钟跑起来

以下命令都在仓库根目录执行。全程不需要 Docker，也不需要单独启动数据库：库文件在第一次 `pc db apply` 时自动创建。

1. 安装依赖。它会生成 `uv.lock`（这个文件需要提交到版本库），并一并装好开发用的工具：

   ```bash
   uv sync                      # 只想要运行时依赖：uv sync --no-dev
   ```

2. 体检。确认环境与文件齐全，并看一眼它认的数据目录与库文件路径：

   ```bash
   uv run python -m pc doctor   # 等价写法：uv run pc doctor
   ```

   还没装依赖时也能体检，那种情况下用 `PYTHONPATH=src python -m pc doctor`。但请**不要**直接跑 `python -m pc doctor`——系统 Python 看不到这个项目，会报 `No module named pc`。

3. 建库。默认写到平台默认的数据目录（见「数据存在哪」），也可以指定别处：

   ```bash
   uv run pc db apply           # 建库：按序号应用全部迁移，每个文件一个事务
   uv run pc db apply --path <文件>   # 只在你想把库放到别处时才需要
   uv run pc db status          # 只读复核：34 张表、两个 FTS5 索引、每个版本的结构指纹
   ```

   **这三条命令在哪个目录运行都行**，不必先 cd 到仓库根：迁移目录与 `config/app.yaml`
   按「项目根」解析（自动向上查找，或用 `--root`/`--dir` 显式指定）。命令会打印它实际
   用的迁移目录，排错时先看那一行。

   两点关于「用哪个 shell」：

   - **Windows（PowerShell / cmd）**：在仓库目录里用 `uv run pc …`。直接敲 `pc …` 不行——
     项目的虚拟环境不在 PATH 上，除非你先 `uv sync` 并激活 `.venv`。
   - **WSL / Git Bash**：`uv` 是 **Windows 侧**装的，Linux 侧没有它，所以 `uv run pc …`
     会报 `uv: command not found`。两种办法：① 用 Windows 的 uv：`uv.exe run pc db apply`
     （在仓库目录里运行即可）；② 直接调虚拟环境里的可执行文件：
     `./.venv/Scripts/pc.exe db apply`。想用原生 Linux 环境的话，在 WSL 里另装一份 uv
     （`curl -LsSf https://astral.sh/uv/install.sh | sh`）再 `uv sync`——那会另建一个
     Linux 虚拟环境，与 Windows 那份互不干扰。

   三点说明：

   - 迁移脚本是**整条语句执行**的写法（文件里既有含分号的注释，也有字符串字面量），所以请用 `pc db apply`，**不要**自己按分号切分。
   - 迁移文件里不允许出现 `PRAGMA`：连接基线（WAL、外键、等待写锁 5 秒等）由程序在建立连接时统一执行，写进 `.sql` 会被直接拒绝。
   - `pc db apply` 按文件名序号应用迁移目录下**全部**未应用的迁移，**每个文件一个事务**：某个文件写错只回滚它自己，之前成功的版本保持有效；已经应用过的版本会自动跳过，不会重复建表，也不会动已存在的数据；结构指纹对不上时只报告、不覆盖。
   - `pc db status` 是只读的：结构不符（缺表、索引不全、外键没开、有未应用的版本、指纹漂移）时退出码 2，并逐条打印哪一项不对。

4. 播种设置项，然后看一遍每个参数现在是多少、从哪来：

   ```bash
   uv run pc config seed        # 首次播种：只插不改，重复运行安全
   uv run pc config show        # 逐项查看生效值与来源（--explain 带含义与影响）
   ```

   `pc config seed` 把 `config/app.yaml` 的 `defaults` 段写进库，**只插入缺失的、绝不覆盖已有的**；
   此后这个实例以数据库为准，再改 `config/app.yaml` 不会影响它。

5. 启动服务，然后打开浏览器：

   ```bash
   uv run uvicorn pc.api.app:create_app --factory --port 8080
   ```

   | 地址 | 用途 |
   | --- | --- |
   | `http://127.0.0.1:8080/` | 索引页：版本、当前阶段、可用端点 |
   | `http://127.0.0.1:8080/healthz` | 存活与版本 |
   | `http://127.0.0.1:8080/api/v1/meta` | 当前运行模式，含 `egress_enabled: false` |
   | `http://127.0.0.1:8080/docs` | 自动生成的接口文档 |

   跳过第 3 步也能启动：服务和体检都不依赖数据库（体检里的「数据库」段只是报告，库文件不存在不会让体检失败）。但要看到设置项的数据库层、以及将来的检索，先做第 3 步。

6. 把你的文件放进去（可选，但这是"真的存进了库"的那一步）：

   ```bash
   # 路线 A：自己随手存的文件，一条命令就行（来源会自动建好）
   uv run pc upload <文件或目录> --note "从哪儿弄来的"
   uv run pc item list

   # 路线 B：官方导出包或积压素材目录（先登记来源，再导入）
   uv run pc source add my-files --kind export --roots <你的目录>
   uv run pc import <你的目录> --source my-files --process
   uv run pc item list
   ```

   两条路的区别只有**身份怎么定**：`pc upload` 按内容（重传同一份不会变成两条，时间留空），`pc import` 按相对路径（重复导入幂等，时间取文件时间）。路线 B 的第一条命令登记来源并写下授权记录（**凭证 + 授权范围 + 授权证明三者齐备才允许采集**，这是设计上的硬要求，不是形式主义；root 自己上传的文件不需要凭证——授权就是"你本人在场"）。文件读进来之后：一条文件一条消息、同名 `.txt`/`.md` 作为配文、`.txt`/`.md` 自己作为文本消息，媒体按魔数校验类型、算 SHA-256 去重、落到 `<data_root>/media`。详见下一节。

## 把你的文件放进去

有两条路，选哪条取决于**这批文件是谁产生的**：

| 你的情况 | 用哪条 | 为什么 |
| --- | --- | --- |
| 手里有一个**导出包**或一大堆积压素材目录，想整体导进去 | `pc import` | 身份按**相对路径**定：同一个文件重复导入是幂等的，时间取文件时间（导出包里那是有意义的线索） |
| **你自己随便存的图**，想随手丢进库（"这张是从哪个群存的？记不清了"） | `pc upload` | 身份按**内容**定：重传同一份内容不会变成两条，改名换目录也算同一条；时间留空（文件时间是你下载它的时间，不是发布时间），来源线索写在 `--note` 里 |

**两条路都不会动你的原文件**：入库是**复制进库**（内容寻址，同一份字节只存一份），源目录只读。

### 官方导出 / 素材目录：`pc import`

```bash
uv run pc source add my-files --kind export --roots D:\素材          # 登记来源（同时写授权）
uv run pc import D:\素材 --source my-files --dry-run                 # 先看会发现什么，不写任何东西
uv run pc import D:\素材 --source my-files --process                 # 真正导入并立刻处理
uv run pc item list --limit 20                                       # 看结果
uv run pc item list --status quarantined                             # 只看被隔离的（见下）
```

### 自己随手存的文件：`pc upload`

```bash
uv run pc upload D:\下载\猫.jpg --note "好像是某个群里的"    # 一条命令：来源会自动建好
uv run pc upload D:\下载\图1.png D:\下载\图2.gif              # 一次多个也行；也可以给整个目录
uv run pc upload D:\下载\猫.jpg                              # 再传一次同一张：报「重复 1 条」，不会变成两条
uv run pc item list --limit 20                                # 备注会显示在「备注」列里
```

关于 `pc upload` 的几点：

- **不需要凭证，也不需要先建来源**：第一次运行会自动建一个叫 `manual` 的来源（`kind=manual`，来源含义是"来源待补"），授权方式是 `root_self`——"授权来自操作者本人在场"。它不是假来源，而是**来源说不清时的正式归档桶**；将来想起来源可以再整理。
- **默认顺手把活干完**（`--no-process` 可以关掉）。这是有意的：库里记的是原文件路径，你上传完顺手把原文件删了，处理阶段就找不到字节了。
- **空文件会被跳过并报告**（0 字节、或者只剩空白的文本文件）。它们凑不出内容身份，硬塞进去会让几个空文件互相顶掉。
- `--note` 是可选的；它记的是**你**知道的来源线索，不会被当成平台信息（平台的"转自哪里"将来走转发链字段）。
- 想上传到一个自己命名的来源，先用 `pc source add <名字> --kind manual` 建好，再 `--source <名字>`。

### 两条路共同的行为

- **一条消息可以含多个内容项**：`cat.jpg` + `cat.txt` 会合成一条"图 + 配文"的消息，拆成两个内容项（文本项 + 媒体项）。
- **不通过安全扫描的内容会被隔离，而不是丢掉**：压缩包、可执行文件、PDF、SVG、脚本，以及魔数认不出的类型，一律进 `<data_root>/quarantine`（与主媒体目录**物理分离**），内容项状态是 `quarantined`，并自动开一条复核任务。被隔离不等于被删除——你可以去看、去决定。
- **扩展名与真实类型不符的内容会通过但被标记**（例如 `.png` 里装的其实是 JPEG）：它不算恶意，但会进复核队列。
- **跳过隐藏文件与符号链接**（`.` 开头、指向别处的链接），并在 `pc doctor` 的能力声明里写明这条规则。
- 两者都只做"落库 + 排队"，真正的取字节/扫描/去重由 `pc work` 完成；`pc upload` 默认顺手跑完，`pc import` 要显式加 `--process`。文件很多时可以分开做，或者用 `pc work --loop` 让它一直跑。
- **同一个文件走两条路**：会有两条消息（身份规则不同、来源也不同），但磁盘上只有一份字节。

## 怎么把东西搜出来

```bash
uv run pc search 雨                  # 一个字的查询也能搜到
uv run pc search 蓝发                 # 两个字（中文最常见的写法）
uv run pc search 蓝发 精灵            # 多个词：两个都要满足
uv run pc search sunset              # 英文按整词匹配，前缀也能匹配（portra 找得到 portrait）
uv run pc search 雨 --source manual  # 只看某个来源
uv run pc search 雨 --tag blue_hair  # 按标签过滤；多个 --tag 是「都要满足」
uv run pc search --since 2026-09-01 --type image --limit 50   # 不带关键词，纯按条件列出
uv run pc search 雨 --sort time      # 按入库时间倒序（默认按相关度）
uv run pc search 雨 --timings        # 打印各段耗时，怀疑慢的时候用
uv run pc search 雨 --json           # 完整字段 + 翻页游标，给脚本或给将来的界面用
```

几件值得知道的事：

- **中文 1~2 个字能搜到**，这是专门做过的：全文索引对少于 3 个字符的查询**不会报错，只会
  安静地返回空**，所以入库时就把每段文字切成了「单字 + 双字」，短查询走另一套索引。
  3 个字以上走子串匹配，可以搜到词中间的内容。
- **默认只看安全、有效、未软删的内容**，同一段文本的重复项折叠成一条。要看被隔离的、
  受限的、重复的，得显式说：`--status quarantined`、`--nsfw-level 2`、`--include-duplicates`。
- **关键词检索不告诉你有多少条命中**，只说"候选 N 条"。这是刻意的：关键词越宽，数总数越贵，
  而这个代价不该由每一次查询承担。纯按条件列表（没有关键词）会给条数，口径分三种：
  `共 N 条`（数完了）、`至少 N 条`（超过 5000 就不再数下去）、`约 N 条`（按标签用量估算）。
- **`--sort time` 不会把关键词丢掉**：它只是把「命中的那些」按入库时间倒序排（默认按相关度）。
- **每页最多 50 条**（`search.default_page_size` 决定默认值，可以调小）。这个上限与检索性能
  预算绑在一起：10 万条内容下，99% 的查询要在 500 毫秒内返回（DESIGN.md §5.6）。
- **每条结果都给出"为什么它出现在这里"**：命中的词、命中在哪一列、带方括号的片段。
- 时间序翻页用 `--cursor`（把上一次 `--json` 里的 `next_cursor` 原样贴回来）；相关度排序
  用 `--page 2` 这样翻。
- **搜不到不等于没有**。先看 `pc doctor` 的 `[检索]` 段：如果它说还有多少条没分词，跑一次
  `uv run pc db reindex --recompute-derived` 再搜（升级前入库的内容都是这种情况）。

## 数据存在哪

**全部持久状态就是一个 SQLite 文件加一个媒体目录**：没有数据库服务、没有连接串、没有端口和密码。库文件叫 `pc.sqlite3`，位置由数据根目录决定，各平台默认值如下：

| 平台 | 默认数据根目录 |
| --- | --- |
| Windows | `%LOCALAPPDATA%\post-collector` |
| Linux | `$XDG_DATA_HOME/post-collector`（缺省 `~/.local/share/post-collector`） |
| macOS | `~/Library/Application Support/post-collector` |

```
<data_root>/
├── pc.sqlite3       事实源：关系数据、任务队列、全文索引、setting 表（-wal / -shm 同目录）
├── media/           媒体本体，按内容哈希分片存放（ab/cd/<sha256>）
├── thumbs/          派生缩略图与 preview，可重建；建议留在 SSD（检索列表每次都读它）
├── cold/            冷层：较早或低频的媒体，可指向 NAS
├── quarantine/      提报隔离区，与 media 物理分离，按期限自动清理
├── backup/          `pc db backup` 的默认落点
└── config/          首次启动生成的配置副本（**尚未实现**，见 DESIGN §10.2）
```

怎么改位置：

- `PC_DATA_ROOT`：改**数据根目录**，媒体、缩略图、备份都跟着它走。
- `PC__DB__PATH`：只改**库文件本身**，媒体仍留在数据根目录（把库放到 SSD 上不该顺带
  把媒体本体挪走——落点变了，老内容一样找不到）。
- `PC__PATHS__MEDIA_ROOT` / `PC__PATHS__COLD_ROOT` / `PC__PATHS__QUARANTINE_ROOT` 等：
  只改**某一个子目录**，把冷层或备份单独放到 NAS 上时用。
- 子目录也可以在 `config/app.yaml` 的 `paths` 段里写死（优先级：进程环境 > `.env` >
  `config/app.yaml` > 从数据根目录派生）。

两个变量都可以写进 `.env`（由 `.env.example` 复制而来，已被 `.gitignore` 忽略，不要提交），
也可以直接设在进程环境里。改完跑一次 `uv run pc doctor`，它会打印实际生效的库文件路径，
以及这个路径是从哪来的。

优先级从高到低是：`--path` > `PC__DB__PATH` > `PC_DATA_ROOT` > `.env` 里的同名两项 >
`config/app.yaml` 的 `db.path` / `db.data_root` > 平台默认。

仓库里的 `data/` 只有在你把数据根目录指向它时才会被用到；默认不用它——运行时产物不放在安装目录，因为安装目录可能只读。

**备份**：库文件用自带命令，不需要停写：

```bash
uv run pc db backup                    # 默认落到 <data_root>/backup/pc-<UTC 时间戳>.sqlite3
uv run pc db backup --to <另一块盘或 NAS 的路径>/pc-20260101T000000Z.sqlite3
```

它用 `VACUUM INTO` 生成一个事务一致的快照，随后打开快照跑完整性检查并核对表数；**拒绝覆盖已存在的文件**（换个文件名，或先移走旧的那份）。两点务必记住：

- **快照必须和库文件放在不同物理介质上**（另一块盘或 NAS）。单文件是 SQLite 最大的优点，也是它最大的风险点——一块盘坏掉会同时丢掉库和它的备份。
- 想要「每天自动备份」还需要自己挂一个计划任务，定时执行上面这条命令；程序目前只提供手动入口。

**媒体**：`media/`、`cold/` 用任何增量备份工具同步到 NAS 或另一块盘即可，文件按内容哈希命名，天然增量。索引、缩略图这类派生数据不用备份，都能重建。

一件事需要说清楚：**`pc.sqlite3` 与媒体目录是唯一必须认真备份的两样东西**，
其它一切（全文索引、缩略图、派生标签）都能从这两样重建。另外，删除功能不会追溯清理已有的备份，
所以「删除后最长 N 天内仍可能存在于备份中」这句必须写进你的隐私策略。

## 参数怎么调

同一个参数只有一个来源，避免出现「改了文件没生效」这类最难查的问题：

| 层 | 位置 | 改它的方式 | 生效 |
| --- | --- | --- | --- |
| 设置页 | 数据库 `setting` 表，字段说明来自 `config/settings-registry.yaml` | 界面点选，中文标签 + 一句大白话说明 + 改了会怎样。**界面在阶段 1**；现在可以用 `uv run pc config show` 看、`uv run pc config seed` 播种 | 立刻生效，不用重启 |
| 开发配置 | `config/app.yaml` | 直接编辑（带注释）。它的 `defaults` 段只在**尚未播种**的实例上生效 | 校验通过后热重载 |
| 部署配置 | `.env` | 编辑后重启进程 | 需要重启 |

规则是：第一次启动时，`config/app.yaml` 里的 `defaults` 段会被用来给数据库写入初始值（这就是 `pc config seed` 做的事）；此后一切以数据库为准。想改默认值就改注册表，别去改已经初始化过的实例。

拿不准某个值是哪来的，就问工具——它逐项回答「现在是多少、为什么是这个值」：

```bash
uv run pc config show              # 六项：相似图片判定严格度、AI 参与程度、内容库最大占用、检索每页条数、匿名提报开关、全局仅本地开关
uv run pc config show --key dedup  # 只看某一项（也可以给命名空间前缀）
uv run pc config show --explain    # 附上「含义 / 影响 / 类型与范围 / 改动后果」
```

输出里的来源只可能是四种之一，按优先级从高到低是：**环境变量 > 数据库 > `config/app.yaml` > 注册表默认值**。看到「数据库 setting 表」就说明这一项已经由设置页接管，改 YAML 对它不再有影响；这也是为什么改了文件没生效时，第一件事应该是跑一次 `pc config show`。

每个设置项都能用环境变量临时覆盖，形式为 `PC__` 加双下划线，例如把检索每页条数改成 50（这是允许的上限）：

```bash
PC__SEARCH__DEFAULT_PAGE_SIZE=50
```

环境变量写错了不会静默失效：如果名字落在某个设置项的命名空间下、但注册表里没有这一项，
`pc config show` 会点名报出来并给出可能的正确写法。（`PC_DATA_ROOT`、`PC__DB__PATH`、
`PC__PATHS__MEDIA_ROOT` 这类属于部署与开发配置段，不在此列。）

现在能调的设置项：相似图片判定严格度、AI 参与程度、内容库最大占用、检索每页条数
（**上限 50 条**，与检索性能预算绑定，见 DESIGN.md §5.6）、匿名提报开关、全局仅本地开关。
数据库文件位置、媒体目录、并发数这类「改错了后果不容易一句话说清」的参数，
刻意只留在配置文件与环境变量里，不放界面。

## 出问题了怎么办

| 现象 | 多半是 | 怎么办 |
| --- | --- | --- |
| `doctor` 报某个文件不存在 | 不在仓库根目录运行 | 回到仓库根，或用 `--root` 指定路径 |
| `python -m pc doctor` 报 `No module named pc` | 用的是系统 Python，没走项目虚拟环境 | 加 `uv run`：`uv run python -m pc doctor`；或临时设 `PYTHONPATH=src` |
| `config show` 提示缺 PyYAML | 还没装依赖 | 跑 `uv sync` |
| 提示「数据目录不可写：…」 | 库文件所在目录没有写权限，或路径指向了只读位置 | 换一个可写目录：设 `PC_DATA_ROOT`（整个数据根目录）或 `PC__DB__PATH`（只挪库文件）；确认当前账号对目标目录有写权限 |
| 提示「打不开数据库文件」或写入时报磁盘相关错误 | 磁盘满了。SQLite 还需要空间写 `-wal` 与临时文件 | 清出空间，或把 `PC_DATA_ROOT` 换到别的盘，然后重启进程；`pc db status` 可用来确认库文件仍能被打开 |
| 启动就被拒绝，提示「你的 Python 自带 SQLite x.y，低于本项目要求的 3.40」 | SQLite 版本门槛没达到，程序是 fail closed 的 | 两条出路：① 升级 Python（3.12+ 一般自带 3.40 以上）；② 改用随 Release 分发的单文件包（自带运行时，不依赖本机 Python）。体检里这一条不影响退出码，但建库会失败 |
| 报 `database is locked` | 有另一个进程正在写同一个库文件，等待超过 5 秒（`busy_timeout`）后主动报错 | 确认没有第二个 `pc` 或服务在跑同一个库；停掉多余的那个。SQLite 是单写者，不要指望两个进程同时写 |
| `pc config show` 说数据库文件还不存在 | 还没建库 | 属正常降级：它照样显示文件与环境层的值，并打印一行说明。要看到数据库层就先 `uv run pc db apply` |
| 改了 `config/app.yaml` 却没生效 | 这个实例已经播种过，一切以数据库为准 | 属设计行为；用 `pc config show` 看来源那一行。要改它的值，等阶段 1 的设置页 |
| 环境变量设了却没生效 | 名字拼错了，或它不属于设置项 | `pc config show` 会点名报出可疑的 `PC__` 变量并提示可能想写哪个；`PC__DB__PATH` 这类部署层变量不在检查范围内 |
| `pc config seed` 说「保留既有 N 项」 | 播种只插不改 | 正常：重复运行不会覆盖任何已有值 |
| `pc config seed` 说库里没有 `setting` 表 | 还没建库 | 先跑 `uv run pc db apply` |
| 媒体/备份/隔离区落在了意料之外的位置 | 某个 `PC__PATHS__*` 或 `config/app.yaml` 的 `paths` 段指到了别处（`.env` 里也可能有旧值） | `uv run pc doctor` 的「运行时目录」段会逐项打印落点与**来源**（`env:` / `.env` / `app.yaml` / 从数据根派生）。注意 `env:` 前缀表示它来自**当前 shell 的环境变量**，优先级最高，`.env` 改它没用 |
| `pc db status` 结论「结构未就绪」、退出码 2 | 缺表、FTS5 索引不全、`journal_mode` 不是 WAL、外键没开、完整性检查没过，或结构指纹漂移 | 按它逐条打印的 `✗` 项处理：索引不完整跑 `uv run pc db reindex` 重建；其余先看下面两行 |
| `pc db status` 提示结构指纹漂移 | 迁移文件在**应用之后**被改过，库里记的指纹与文件对不上 | 本工具不会自动改库，也不会覆盖指纹。若改动确有必要，请以新迁移追加，而不是改已应用的版本；否则把文件改回原样即可 |
| 库确实建坏了（半成品状态） | 有表但记账不完整，或记账与表不一致 | 工具不会自动修补。先 `uv run pc db backup --to <别处>` 留档，再删掉这个库文件重建：`uv run pc db apply` |
| `pc db backup` 说「备份目标已存在，拒绝覆盖」 | 同名快照已经有一份 | 换个文件名，或先移走旧的那份——刻意不覆盖，避免静默丢数据 |
| 想把库恢复到某个快照 | 需要回滚 | ① 停掉所有 `pc` 进程；② 把现有库文件复制一份留档；③ 把快照复制**成** `<data_root>/pc.sqlite3`；④ 删掉同目录残留的 `pc.sqlite3-wal` / `-shm`，否则会与快照不一致；⑤ `uv run pc db status` 复核后再启动服务 |
| 启动报端口被占用 | 8080 有别的程序 | 换端口 `--port 8081` |
| 老终端里中文显示成方块 | 终端编码不是 UTF-8 | 命令输出已强制 UTF-8；换个终端或执行 `chcp 65001` |
| `pc db apply` 报「找不到迁移目录」 | 用的是 `uv tool install` 装的包（它没带迁移文件），或 `--dir`/`--root` 指到了不存在的地方 | 从仓库源码目录运行即可（迁移目录按项目根解析，不依赖当前目录）。三条出路在报错里都列着：在仓库根运行 / `--dir <绝对路径>` / `--root <仓库根>`。随包分发迁移文件属于已知缺口，见 AGENTS.md |
| bash / WSL 里 `uv: command not found` | `uv` 装在 Windows 侧，Linux 环境里没有 | 用 `uv.exe run pc …`，或直接 `./.venv/Scripts/pc.exe db apply`；也可以在 WSL 里另装一份 uv 并 `uv sync`（会另建一个 Linux 虚拟环境） |
| `pc import` 说「来源未通过授权校验」 | 这个来源没有有效的授权记录（凭证 + 范围 + 授权证明三者齐备才允许采集） | `uv run pc source list` 看授权状态，确认它没过期、没被撤销；必要时重新 `pc source add`（它会同时写下授权记录） |
| `pc import` 说「找不到这些路径」 | 路径写错，或用了相对路径但当前目录不对 | 用绝对路径；Windows 上注意 `D:\素材` 这种反斜杠路径在 PowerShell 里不需要转义，但在某些终端里要加引号 |
| `pc import` 说「暂不支持这种来源类型」 | 登记来源时 `--kind` 选了一个还没实现的类型（`bot_api`/`webhook`/`rss`/`user_api`） | 现在只有 `export`（本地文件/官方导出目录）可用；平台型连接器在阶段 2 |
| `pc item list` 是空的，但导入说成功了 | 任务还在排队：导入只落库 + 排队，取字节由 `pc work` 做 | 跑 `uv run pc work`，或下次导入时加 `--process` |
| 内容状态是 `quarantined` | 安全扫描没放行（压缩包/可执行文件/PDF/SVG/脚本/魔数认不出），或扩展名与真实类型不符 | 属预期行为：字节在 `<data_root>/quarantine`，与主媒体目录物理分离，并自动开了一条复核任务。想放宽某类限制改 `config/app.yaml` 的 `security` 段（例如 `allow_svg`） |
| `pc work` 报「死信」 | 确定性失败：文件已不存在、超过字节上限、命中哈希墓地（该内容曾被硬删）、来源类型没实现 | 看它打印的原因。这些重试也不会好，所以直接进死信而不是反复重试；偶发错误才退避重试 |
| 导入的目录后来移动了，`pc work` 报找不到文件 | `media_refs` 里存的是当时的路径 | 把目录放回原处再跑 `pc work`，或重新导入一次（内容相同的字节不会重复占盘） |
| `pc upload` 报「跳过 N 个文件」 | 那些文件是 0 字节、或者只剩空白 | 这是有意的：空文件凑不出内容身份。补上内容再传一次即可 |
| `pc upload` 说「来源不是 manual」 | `--source` 指到了一个 `kind=export` 的来源 | 别加 `--source`（用默认的 `manual` 来源），或 `uv run pc source add <名字> --kind manual` 另建一个。手工上传要按内容定身份，换来源会改成按路径定身份 |
| 重传同一张图，`pc upload` 说「重复 1 条」 | 身份按内容算，这是设计如此 | 想让它成为**另一个**条目，说明它们是不同的东西（例如配了不同的文字）；只改文件名不会产生新条目 |
| `pc upload` 之后立刻删了原文件 | 库里记的是原文件路径 | 默认已经顺手处理完了，所以通常没事；如果用了 `--no-process`，处理前别删 |
| `pc search` 说「没有匹配的内容」，但内容明明在 | 三种可能：默认只看安全有效内容（被隔离/受限/软删的不出现）；老数据还没分词；关键词确实不在文本里 | ① 试 `--status quarantined` 或 `--nsfw-level 2`；② 跑 `uv run pc doctor` 看 `[检索]` 段，若提示"还没有分词结果"就跑 `uv run pc db reindex --recompute-derived`；③ `uv run pc search --json`（不带关键词）确认内容真的在库里 |
| `pc search` 的中文 1~2 字查询搜不到 | 老数据是在分词功能之前入库的，`text_search` 是空的 | `uv run pc db reindex --recompute-derived`（分批重算 + 重建索引，可反复跑） |
| `pc search` 说「候选 N 条」「结果可能不完整」 | 关键词检索只在相关度最高的前 500 条候选里做过滤（不够时升到 2000） | 属设计行为（DESIGN §5.6 M1）：加上更具体的词、或加 `--source`/`--tag`/`--since` 把范围收窄；宽泛的单字查询命中太多时一定会有这个提示 |
| `pc search --limit 100` 被拒绝 | 每页上限 50 与性能预算绑定 | 用 `--page 2` 翻页，或调小 `search.default_page_size` 之外的用法都不行——这个上限不开放 |
| `pc search` 说「翻页游标坏了」 | `--cursor` 的值不是上一次结果里的 `next_cursor`（可能抄错或被截断） | 重新查询，从 `--json` 输出的 `next_cursor` 原样复制；相关度排序请用 `--page` |
| `pc search --tag` 说找不到标签但标签确实有 | 标签名必须完全一致（大小写与空格都一样），或者需要 `命名空间:名字` 的写法 | `--tag blue_hair`；报错里会给出最接近的几个标签名 |
| 报错看不懂 | 缺少上下文 | 把 `doctor` 的输出贴进 issue，它已包含脱敏后的环境信息 |

缩略图与感知哈希（所以列表里暂时没有图可看，检索结果也不会给缩略图地址）、
链接自动抓取、AI 外发、向量检索（所以还不能以图搜图）、多租户、Meilisearch 与 MinIO、Web 界面（包括**设置页**：现在只能用命令行查看与播种设置项，
改值要等界面）、**平台型来源**（微信 / QQ / Discord / Telegram 等：接口与工厂已经留好，
`kind` 也登记在案，但实现要等阶段 1 的检索闭环站稳；**它们还需要凭证存储与系统密钥库先落地**，
所以 root 手工上传刻意做成"不需要凭证"的那一类，不被它挡住）、**备注的事后编辑**（上传时能写、
列表里能看，改还得等界面）、**把条目从一个来源改挂到另一个来源**、**备份的定时调度**（手动入口
`pc db backup` 已经有了，缺的是每日自动执行）、**匿名提报入口（设计与代码里都后置到阶段 2，见下）**。

测试覆盖了数据库适配层、SQLite 行为契约、迁移器、配置与路径解析、连接器/存储/扫描器、
服务层与 CLI 端到端（导入、上传、检索各一条）、检索的过滤/分页/可解释性与"没有 N+1"的语句计数、
检索性能基准脚本本身、设置层、schema 红线，以及**「全库不存在出网代码路径」这条守卫**；
打标还没有测试，因为那一块还没有实现。

模型与 AI 也一样：默认设置下不会下载或加载任何模型，**缺模型是正常状态，不是故障**。
启用本地模型后，权重只从官方仓库按固定 revision 拉取，下载完先校验 SHA-256 再加载，
不匹配就拒绝加载并告警；换模型或 prompt 版本后旧标签不删除，新结果追加保存，
并可按新版本重算。这套供给与升级路径见 DESIGN.md §4.10，目前尚未接线。

设置项的写入路径已经在代码里就绪（带前后值审计、失败整体回滚、危险项二次确认与「改动前先 dry-run」的闸门，都有集成测试盯着），但**没有从命令行改设置的入口**：审计表要求写清「这次改动从哪来」，而它的取值里目前没有「命令行」这一类，硬塞进去只会让审计记录失真。设置页（界面）是它的第一个正经消费者。

阶段 1 要做的是打通第一个可用闭环：**导入 / 手工上传 → 安全扫描与去重 → 存储 → 打标（可选）→ 检索 → 人工纠错**，全部本机运行，**且不开放任何公开入口**（只启用 root 与邀请制用户）。这个闭环**已经打通了大半**：导入、安全扫描、精确去重、内容寻址存储、任务队列与 worker、查看与**命令行检索**都已经可用（见「把你的文件导进去」与「怎么把东西搜出来」）；还差打标、人工纠错界面，以及把检索端上界面（检索服务与适配器已经就绪，缺的是一条 HTTP 路由与页面）。验收标准写在 DESIGN.md §9，其中与安全直接相关的断言级要求包括：全库不存在任何外发调用路径；硬删后的哈希墓地仍能拦截重复导入、且墓地里查不到原内容的元数据；媒体的删除只在引用计数为零时发生。前两条**已经守住**：三张阶段 2 的表（`content_embedding`、`ai_provider_policy`、`egress_log`）在库里必须缺席，`content_item.egress_state` 的默认值必须是 `local_only`，`inbox_item` 不允许存在任何通往 `content_item` 的列或外键，`src/pc/**` 不允许出现任何出网模块的导入，墓地对重复导入的拦截有端到端测试——这些都有集成测试盯着。引用计数删除要等内容删除功能落地（阶段 1 剩下那部分）。

**匿名提报（L2）在设计与代码里都已后置到阶段 2**，原因很实际：把本地工具变成公开内容入口，会同时带来公网暴露、滥用、内容投毒，以及举报与下架方面的义务，而隧道（Tailscale/Cloudflare）只解决可达性、不解决这些义务。阶段 1 因此**不监听非本机地址**（首次初始化未完成时尤其如此），数据库里的 `inbox_item` 只是为阶段 2 预留的表结构。

## 落地前需要你确认的事

技术上能做的已经做了，剩下的是**只有你能拍板**的部分。建议在正式导入数据前逐项过一遍 DESIGN.md 附录 A：

- 目标平台的接口条款、Bot 权限范围、历史消息可读性、速率限制；
- 所选模型权重的许可证是否允许你的使用场景（启用本地模型前先确认）；
- 你所在司法辖区对采集、存储、处理他人内容与个人信息的要求；
- 如果打算开放匿名提报入口：你可能因此承担内容存储与下架相关的义务，先确认再开；
- 滚动删除与删除权的冲突：硬删后仍会保留内容哈希（用于防止同一内容被反复导入），确认这在你这里可接受；
- 备份到底放在哪块盘或哪台 NAS 上：它必须与库文件分开，且要定期真的试着恢复一次。

想改代码、加模块、写迁移，请先读 [`AGENTS.md`](AGENTS.md)；想知道某个设计为什么是这样，读 [`DESIGN.md`](DESIGN.md)。
